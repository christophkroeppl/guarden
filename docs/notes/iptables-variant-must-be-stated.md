# Which iptables table guarden's rules land in, and why guarden states it

**Status: measured on a real machine, decided, implemented. The mechanism named
in ticket 260 was WRONG, and the correction makes the defect worse before it
makes it fixable.**

## What the ticket 260 note said, and what is actually true

Ticket 260's "A second, separate finding" said:

> `ferm` invokes `iptables` by name, so whichever the alternatives system says at
> the time is the table that gets written.

**That is false, and it is false in the direction that matters.** `ferm` does not
consult `update-alternatives` at all. From `find_tool` in `/usr/sbin/ferm`
(ferm 2.7, read out of the installed binary):

```perl
sub find_tool($) {
    my $name = shift;
    return $name if $option{test};
    my @path = ('/usr/sbin', '/sbin', split ':', $ENV{PATH});
    if ($name =~ /^(.*tables)(.*)$/) {
        # prefer the "legacy" xtables tools the new nft based tools
        # are incompatible and sometimes break ferm
        my $legacy_name = $1 . '-legacy' . $2;
        foreach my $path (@path) {
            my $ret = "$path/$legacy_name";
            return $ret if -x $ret;
        }
    }
    foreach my $path (@path) {
        my $ret = "$path/$name";
        return $ret if -x $ret;
    }
    die "$name not found in PATH\n";
}
```

For any name matching `tables`, the **`-legacy`-suffixed binary is preferred
first**, on a fixed path list that does not include the alternatives resolution
at all. Measured on the golden:

```
$ ferm --shell /etc/guarden/firewall/.combined.conf | head -1
/usr/sbin/iptables-legacy-restore <<EOT
# Generated by ferm 2.7 (iptables-save) on ...

$ update-alternatives --query iptables | grep ^Value
Value: /usr/sbin/iptables-nft

$ iptables --version
iptables v1.8.11 (nf_tables)
```

**So on a perfectly healthy host, with the distribution's default selection, the
two halves already disagree.** ferm writes legacy; `/usr/sbin/iptables` reads nft.

And the disagreement is **not** fixed by setting the alternative. Measured on the
same host:

```
$ update-alternatives --set iptables /usr/sbin/iptables-nft   # already the value
$ systemctl restart guarden-firewall.service
$ iptables -S guarden-in
iptables: No chain/target/match by that name.
$ iptables-legacy -S guarden-in
-N guarden-in
```

Setting it to `legacy` *does* make the two agree — and only because ferm was
already writing there:

```
$ update-alternatives --set iptables /usr/sbin/iptables-legacy
$ systemctl restart guarden-firewall.service
$ iptables -S guarden-in
-N guarden-in
```

The conclusion inverts the obvious fix. **The obvious answer — "converge nft,
because nft is the modern one and it is what the alternatives names by default" —
does not work and would make things worse.** ferm would keep writing legacy, so
selecting nft would leave the host's own `iptables` reading a table guarden had
stopped writing: the fail-open with the diagnostic claiming it was fixed.

## The other measured half: it is ferm's choice, and it is fragile

The fallback branch matters for hosts where the `-legacy` names are absent. With
`iptables-legacy*` moved off the host, ferm resolved the unsuffixed name instead:

```
$ ferm --shell … | head -1
/usr/sbin/iptables-restore <<EOT
```

and the rules landed in **nft** — `nft list tables` then answered `table ip filter`
and `table ip nat`, where before it answered nothing. **So the table guarden's
rules land in is decided by which binaries happen to be installed on the host, at
the moment ferm runs.** That is the whole defect, and it is not a matter of
configuration at all.

A host that has `iptables-legacy*` installed gets legacy. A minimal image without
it gets nft. Both are "a Debian-family host", and neither is wrong on its own
terms; what is wrong is that guarden never chose.

## The decision

**Guarden converges ONE named variant, and the variant is `legacy`.**

Three reasons, in the order they decided it:

1. **It is the table ferm actually writes on a host with both binaries.** Any
   other choice means selecting a variant ferm is not going to honour, and the
   selection becomes a claim about the host rather than about guarden.
2. **`legacy` is where the rules already are**, so the selection moves the
   *reader's* side of the pair rather than fighting the writer's. The whole
   problem is that the reader and the writer disagree; aligning the reader to the
   writer is one command and cannot half-work.
3. **The alternative would require removing `iptables-legacy*` from the host to
   make ferm choose**, which is a mutation of the host's package state performed
   to satisfy a firewall decision. Not acceptable, and not needed.

The cost is stated rather than hidden: **guarden's rules live in a table the
distribution's default `iptables` does not read**, and the price is paid by
`update-alternatives` pointing operators at the same table. A host that ships only
one variant needs no selection at all. A future ferm that stops preferring legacy
is caught by the readability check below rather than by this row going quietly
stale.

## Which of the two shapes the ticket offered

The ticket offered: (a) verify the rendered rules are readable through the host's
own binary and fail loudly, or (b) explicitly select a variant.

**Both, and neither alone is enough — which is the finding.**

Selecting the variant is necessary: without it there is no converged state, only
a host that happens to agree. But selection alone is **provably insufficient on
this host**, because the selection is not what ferm reads. Selecting nft on the
golden produces a firewall in one table, an operator reading the other, and every
tool reporting success — the fail-open with a green check. A selection that cannot
be verified is a preference.

Verifying readability alone is insufficient too: a check that reports a mismatch
and does not correct it leaves every host in permanent drift and converges
nothing, and the phase would fail forever on the golden itself.

So the phase carries **two items in a fixed order**:

1. `this host's own iptables is the legacy variant guarden converges` —
   `--apply` runs the list's `set` argv (`update-alternatives --set iptables
   /usr/sbin/iptables-legacy`), `--check` reports it as drift. This is the
   necessary half and it is the one that makes the reader agree with the writer.
2. `guarden-firewall.service is enabled, and is running with guarden's rules
   readable through this host's own iptables rather than in another table` —
   `--apply` starts the unit, and the item holds only when the unit is active
   **and** `iptables -S guarden-in` answers exit 0 through the host's own binary.
   This is the sufficient half, because it asks the question of the rules
   themselves rather than of the selection.

**Ordering is load-bearing in both directions.** The variant must be selected
before the unit starts, because starting the unit is what makes ferm resolve the
binary and load the policy — a firewall loaded into legacy and then "fixed" by
switching alternatives leaves the box with a rule set nobody is reading. And the
readability check must come after the start, because before it there is nothing
to read and an absent chain is not yet evidence of a mismatch.

**The readability check reads the chain, not the alternatives, deliberately.**
`update-alternatives` is where a host records which variant `/usr/sbin/iptables`
*names*; ferm is what actually *loads* the policy. Those are two different facts
and only the second one says where the firewall is.

## What a host that disagrees does

| host state | `--check` | `--apply` |
|---|---|---|
| alternatives names `legacy`, rules readable | exit 0, silent | exit 0, no-op |
| alternatives names `nft`, rules in legacy (the golden's starting state) | **exit 1**, `drift: this host's own iptables is the legacy variant guarden converges` | selects `legacy`, then loads; exit 0 |
| alternatives names `nft`, and ferm wrote nft anyway | **exit 1** on the same drift line, and the readability item does not hold either | selects `legacy`, then ferm keeps writing nft, and **the readability item still reports drift** |
| the list's family states no `variant` | **exit 2**, naming the gap and the families the list does carry | exit 2 |

The third row is the point of having two items. On a host where ferm's resolution
has changed, selecting `legacy` does not move ferm, and **the phase says so rather
than reporting a converged firewall whose rules the host cannot read.** That is
the failure this whole note exists to prevent, and it is now an exit 1 with a
sentence naming the table rather than a silent success.

**A family with no `variant` is exit 2, not exit 1.** The list is a repository
input; a row nobody filled in is not a host out of state, and a check reporting it
as drift would report it on every Fedora host forever while converging nothing.
Only Debian states one today — Fedora and Arch ship `iptables-legacy` under the
unsuffixed name with no alternatives mechanism to select against, which is a
different host shape and not something the list can paper over.

**That exit-2 path is not reachable from a Debian host, and this is stated rather
than papered over.** `--family` is `soil packages`'s and only with `--list` or
`--render-user-data`; `soil firewall --check --family fedora` is refused by the
argument parser before the firewall phase builds a single item (exit 2,
``--family is `soil packages`'s, and only with --list or --render-user-data``), and
`soil packages --list --family fedora` succeeds because the list reader resolves
the family without ever asking which variant it converges. **So the suite asserts
the reachable refusal and states plainly that the no-variant refusal needs a
Fedora host.** Reaching it by faking the family — a scratch `packages.toml`, a
`--family` that lies — would be a fake, and this repository has paid for three.

## A harness bug this work found, which is NOT mine to fix

`tests/t20-firewall-variant.sh` declares `# machine: fresh` and the harness
**runs it on a shared machine anyway.** Measured, not read:

```
$ sed -n 's/^# machine: //p' tests/t20-firewall-variant.sh
fresh
$ tests/lxc.sh run t20-firewall-variant --fresh --no-cache
note: --fresh cuts a machine per file and overrode the shared declaration of 1 suite(s)
```

`--fresh` prints that override note for a suite that is already declared
`fresh`. `_needs_fresh()` in `tests/lxc.sh` returns 0 for both `''` and `fresh`,
and the caller at line 665 reads it backwards:

```sh
want_fresh=1
_needs_fresh "$file" && want_fresh=0     # the name says "needs fresh"
```

So a suite declaring `fresh` is assigned `want_fresh=0` and lands in the shared
group. **The comment directly above that code says the opposite** — "An absent
declaration is `fresh`, and that is the whole of the safety argument" — so the
inversion makes the documented safety property false: `tests/t20-firewall.sh`
declares nothing, runs on the shared machine, leaves `guarden-firewall.service`
enabled pointing at `legacy`, and the next `fresh` suite that expects a pristine
host inherits a converged firewall.

**Not fixed here.** `tests/lxc.sh` and `tests/lib.sh` are a sibling agent's, per
the task brief. It is theirs to fix and it is worth fixing before the two
branches merge, because my suite's green and a suite that follows it are both
claims about a machine neither asked for.

My suite is therefore **verified with `--fresh`**, which forces the isolation its
declaration asks for and cannot itself be affected by the bug. It also restores
the host's alternatives selection in an `EXIT` trap, so it is safe to run on a
shared machine even while the harness bug stands.

## Where it is stated in the repository

- **`packages/packages.toml`** — a `[families.<family>.variant]` subtable per
  family, carrying `name`, `set` and `report`. The argvs live in the list beside
  `install`/`query`/`update` for the reason those do: the mechanisms differ per
  family and a command written in code is a second place they differ.
- **`src/guarden/packagelist.py`** — `variant_table`, `variant`, `variant_argv`,
  `variant_name`. `variant()` is the rejection point, and it names the first
  missing field of a partial row rather than acting on a preference it cannot
  select.
- **`src/guarden/hostprep.py`** — the two items in `firewall_items`, in that
  order, plus `_host_variant`, `_variant_selected`, `_select_variant`,
  `_rendered_rules_readable`, `_firewall_applied`.
- **`src/guarden/userdata.py`** / **`tools/cloud-init/user-data.yaml`** — the
  rendered cloud-init document records both halves (what the host's `iptables`
  names, and what ferm would load) into the evidence directory **before any
  phase runs**, so a machine that boots into the two halves disagreeing says so
  at that moment rather than after six phases report success.
- **`tests/t20-firewall-variant.sh`** — the assertions, including the mismatch as
  a test case rather than as prose.

## NOT changed, and why

**`src/guarden/rules.py` and the firewall's actual rules.** The sibling agent owns
those and is working on the loopback deny. This is about which table the rules land
in, not what they say.

**`docs/spec.md` and `docs/adr/`.** The spec says `ferm` is the firewall guarden
runs, which is still true; it does not say which iptables variant, so this is an
absence rather than a contradiction. **A spec sentence stating the variant belongs
in an ADR** — the choice trades a modern table for a working one, and that trade
is exactly what an ADR is for. This note records the measurement and the decision;
it is not the authority.

## Not yet measured

- **Whether `update-alternatives --set` survives a reboot.** The suite asserts the
  unit is enabled, and `update-alternatives` state lives in
  `/var/lib/dpkg/alternatives/`, so it should — but no run here has rebooted a
  converged host and asked. Worth one check before this is called done.
- **Whether `ferm -F` (the unit's `ExecStop`) flushes the same table it loaded.**
  It resolves the binary the same way, so it should; again unmeasured on a reboot.
- **Fedora and Arch.** Stated as unreached, not as working. The list says so and
  the phase refuses them, which is an honest position rather than a claim — and
  the suite cannot reach that refusal from a Debian host, because `--family` is
  `soil packages`'s. Testing it needs a Fedora machine.
- **The `iptables-nft` mutual-exclusion assertion when the host ships only one
  variant.** The suite skips that assertion where `iptables-nft` is absent rather
  than asserting an absolute, so on a single-variant host it goes vacuous by
  construction. Stated because a vacuous assertion is a claim nobody made.
