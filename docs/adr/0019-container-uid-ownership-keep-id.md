# Container uid vs host ownership: map the image user onto the service identity, never chown

guarden's isolation boundary is one host uid per service and its 0700 tree, but a rootless
container's non-root image user maps into the service's subuid band, so image-uid writes are
denied on entry and, if allowed, would land on disk as subuid-aliased owners. We decided that
guarden probes the image's declared user at first start and renders
`Userns=keep-id:uid=...,gid=...` into the unit itself — moving the process's mapping onto the
service identity — instead of ever chowning files. Operator decision locked 2026-10-18 after a
measured option review; this ADR supersedes the spec's blanket refusal of `Userns=` for
guarden-generated lines (repository-supplied `Userns` stays refused).

## Status

accepted (2026-10-18, operator)

## Considered Options

All options were evaluated against the standing constraints: do not change uid/gid inside
containers, keep the service uid + 0700 tree as the isolation boundary, no major platform
changes for a deployment. Measurements were taken on the live boxes (podman 5.7.0, kernel
6.9.3): default map is container 0 -> service uid, container 1..65536 -> subuid band
(aliases measured 306608 for uid 10001, 1017603 for uid 100); `keep-id:uid=70,gid=21`
delivered WRITE_OK into a 994-owned 0700 dir with files landing owned by the service user.

- **A1 manual namespace chown (rejected).** What the Q27 redeploy actually needed: 12 manual
  steps per stack, subuid arithmetic in the runbook, and a re-ingest re-chowns `state/*` back
  and re-breaks a working deployment.
- **A2 whole-volume automatic chown (rejected).** Automates A1's constant: still moves file
  ownership forever, one owner per volume cannot serve two image uids, and drift checks would
  chase it.
- **A3 subdir-scoped chown (kept as the fallback).** Chown only the manifest-declared writable
  subdir, skipping `.snapshots/` (ticket 273's rule). Smallest wound, still a wound; sanctioned
  for images whose entrypoint misbehaves under keep-id, together with a per-service owner
  override as the manual escape hatch.
- **B1 keep-id generated by guarden (DECIDED).** Probe `image inspect Config.User` at first
  start, render one quadlet line, record the probed uid/gid in the registry. No file is ever
  touched, the image's USER is untouched, re-ingest has nothing to re-chown, and a shared
  volume works because each unit maps its own user onto the same service identity.
- **B2 User=0 (rejected).** The default map already makes container root the service user, but
  it overrides the image's declared uid — forbidden by constraint — and images that drop
  privileges fall back into the subuid band anyway.
- **B3 pin the service's uid to the image's uid (rejected).** Agreement by construction, but
  the uid must be known at user creation, images rebase across versions, and host uid
  allocation becomes image-dependent.
- **C1 idmapped mounts (held).** Cleanest in theory (kernel translates at the VFS boundary,
  nothing moves), but currently disqualified: LSM hooks do not receive mount idmaps (LWN
  1092727, series only entering v7.4), CVE-2026-64294 sits in exactly these ownership checks
  with stable fixes at 6.6.144+/6.12.95+ while this host runs EOL 6.9.3, and the surface is
  churning. Re-eligible after a kernel carrying both the LSM-idmap series and the CVE fix;
  the capability probe report is probe-idmap-capability.md and probe-idmap VM is kept for the
  re-run.
- **C2 POSIX ACLs (rejected).** Keeps ownership at 994 and grants the alias entry-by-entry,
  but guarden has no ACL layer (create, drift, snapshot preservation, docs), `ls` hides the
  guest list, and the tree's owner can always alter its own ACLs — new surface without new
  assurance.
- **C3 classic group permissions (rejected).** One group slot per door loses on shared
  volumes; the operator declined it.
- **D restructure writes to service-owned paths / tmpfs (rejected).** Per-application work
  that does not generalize.

## Consequences

- The unit gains a guarden-generated `Userns=keep-id:uid=...,gid=...` line, rendered after the
  first probe; the registry records the probed uid/gid, which is also the owner_uid ticket 277
  wanted for drift. Re-ingest can no longer break ownership because nothing chowns.
- Entry points that start as root and then drop (the stock postgres pattern) are the one
  unmeasured class under keep-id; they are a named acceptance test in the implementation, not
  an open design question.
- The spec and AGENTS.md refusal wording for `Userns=` must be scoped to repository-supplied
  input; loom-generated lines are the only ones allowed. AGENTS.md is a protected file — its
  edit is a separate operator-approved change.
- Fallback stack: A3 subdir chown with `.snapshots/` skipped, plus a per-service owner override
  for volumes shared by two images. C1 stays on the shelf until the kernel preconditions above
  hold.
